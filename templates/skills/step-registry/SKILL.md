# Step Registry System

This project uses a custom TypeScript AST-based step registry that indexes all step definitions, page objects, and features into a searchable JSON file. **This is the ONLY way to discover existing steps — NEVER use grep, ripgrep, or file search.**

## Why the registry exists

- Step definitions use regex patterns which are hard to search with text tools.
- The registry provides fuzzy matching against step descriptions, not just literal text.
- It tracks relationships: which steps use which page objects, which features exercise which steps.
- It enables the AI agent to quickly find reusable steps without scanning hundreds of files.

## Searching the registry

Use the repo's registry aliases (confirm in `AGENTS.md`):

```bash
# Find steps matching a description
pnpm registry:search --step "add to cart"
pnpm registry:search --step "login"
pnpm registry:search --step "verify price"

# Find page objects
pnpm registry:search --page "checkout"
pnpm registry:search --page "product"

# Find elements on page objects
pnpm registry:search --element "submit button"
pnpm registry:search --element "price display"

# Find features by name or tag
pnpm registry:search --feature "wishlist"
pnpm registry:search --feature "@sanity"
```

Results show: file path, line number, regex pattern, step type (Given/When/Then), parameters, and related page objects. Maximum 10 results per search.

## Registry structure (`src/.step-registry.json`)

```json
{
  "steps": [
    {
      "pattern": "/^I add the product \"(.+)\" to my cart$/",
      "type": "When",
      "file": "src/steps/cart.steps.ts",
      "line": 42,
      "params": ["productName: string"],
      "pageRefs": ["cartPage", "productPage"]
    }
  ],
  "pages": [
    {
      "class": "CartPage",
      "file": "src/pages/CartPage.ts",
      "elements": ["addButton", "removeButton", "cartTotal", "itemCount"],
      "methods": ["addItem", "removeItem", "getTotal", "getItemCount"]
    }
  ],
  "features": [
    {
      "file": "src/features/e2e/checkout/add-to-cart.feature",
      "tags": ["@checkout", "@sanity"],
      "scenarios": ["Add single item to cart", "Add multiple items to cart"]
    }
  ]
}
```

## Regenerating the registry

Run after ANY change to step definitions, page objects, or feature files (alias per `AGENTS.md`):

```bash
pnpm registry:gen
```

This runs the TypeScript AST parser over:
- `src/steps/**/*.ts` — extracts regex patterns, types, params, page object references
- `src/pages/**/*.ts` — extracts class names, elements objects, public methods
- `src/features/**/*.feature` — extracts file paths, tags, scenario names

The registry is also auto-regenerated by the pre-commit hook (lint-staged).

## When to add a new step vs reuse

**ALWAYS search first.** Before writing a new step definition:

1. Search the registry for the action you need: `--step "click submit"`, `--step "verify text"`, etc.
2. If a match exists with the same semantics, **reuse it** — even if the wording differs slightly.
3. If no match exists, check for a more general step that accepts a parameter (e.g., `I click the "(.+)" button` covers many buttons).
4. Only create a new step if no existing step covers the action AND no generalization makes sense.

### Signals to create a new step:
- The action involves a page-specific interaction that no general step covers.
- The action requires multiple page object calls that should be atomic.
- The assertion checks a domain-specific condition not expressible as a generic comparison.

### Signals to reuse an existing step:
- The registry shows a step with matching regex that accepts a parameter for your variant.
- A slight rewording of your Gherkin can match an existing pattern.
- The existing step delegates to the same page object you'd target.

## Step definition conventions (for new steps)

```typescript
import { createBdd } from 'playwright-bdd';
const { Given, When, Then } = createBdd();

// ALWAYS use regex patterns — Cucumber expressions are FORBIDDEN
When(/^I add "(.+)" to my cart$/, async ({}, productName: string) => {
  await cartPage.addItem(productName);
});

Then(/^the cart should contain (\d+) items?$/, async ({}, count: string) => {
  const itemCount = await cartPage.getItemCount();
  assert.equal(itemCount, parseInt(count));
});
```

### Rules:
- Regex patterns only: `/^pattern$/` with capture groups for parameters.
- First param is always `{}` (empty fixtures destructuring from playwright-bdd).
- Delegate ALL browser interactions to page objects — never use `page.*` in steps.
- One assertion per `Then` step.

## Do / Don't
- DO search the registry before every new step definition.
- DO regenerate the registry after changes (`pnpm registry:gen`).
- DO reuse existing steps with parameters rather than creating near-duplicates.
- DON'T use grep, ripgrep, or file search to find steps — they miss regex patterns.
- DON'T create a step that duplicates an existing one with slightly different wording.
- DON'T write browser interactions directly in steps — always delegate to page objects.
